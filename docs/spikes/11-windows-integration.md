Date: 2026-10-21

## 1. Question

The rules this spike settles: APP-014, APP-020, APP-022, APP-146, ARCH-127, CORE-160 and QA-088, and, for the desktop test group, QA-042. ARCH-127 is the keep-awake rule plan 4a's Task 2 adds; Appendix G is the spec appendix the same task writes.

The questions, one per check:

- Which `windows` 0.62 features does the suite need for toasts, the shortcut, Windows Hello, the fullscreen state and the power request? (S1.1)
- Can a windowless, detached process post toasts under the AUMID of a per-user Start-menu shortcut? (S1.2)
- What exactly does a protocol activation's raw command line hold: from a toast's body, from its button, from a browser and from the Run dialog? (S1.3)
- Which foreground recipe brings the running instance to the front when a toast click starts a second launch? (S1.4)
- Do progress toasts update in place, without popping again, and behave as documented once dismissed or removed? (S1.5)
- What does `SHQueryUserNotificationState` report at the desktop, in a fullscreen Direct3D program, in fullscreen video and in a slide show, and how fast is it? (S1.6)
- Which power-request API keeps the PC awake while a GPU job runs, and does the core see a sleep and a wake? (S1.7)
- Which Windows Hello route can `lil dev approve` use: a key-encryption key from a Hello signature, DPAPI behind a Hello check, or a passphrase only? (S1.8)
- Which of these desktop checks work inside Windows Sandbox, unattended, and how long does a run take? (S1.9)

## 3. Method

`spikes/winshell/` is a standalone crate (not a workspace member) with four binaries:

- `winshell-core` (`windows_subsystem = "windows"`) is the windowless sender. It is always started with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` and no inherited handles (`CreateProcessW` with `bInheritHandles = FALSE`: `std::process::Command` passes TRUE, and the child then holds its caller's stdout pipe open, so a caller that reads it to EOF waits for the child to exit; `tests/spawn_detached.rs`), as `lil-client` starts the core, and writes its result as JSON to the file `--out` names. It posts toasts (Appendix G's XML: `launch` with `activationType="protocol"`, an "Open" action for the confirmation form, Tag and Group, `SuppressPopup`), runs the progress toast (data binding, `NotificationData` with `SequenceNumber` 1 and one update a second by Tag and Group), `Remove(tag, group)`, the 2 s `SHQueryUserNotificationState` poll with 100 timed calls, and the power request: `PowerCreateRequest` with a simple reason string and `PowerSetRequest(PowerRequestSystemRequired)` (or, on the FAIL path, `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` from a dedicated thread), held until a flag file appears, with a hidden top-level window that logs every `WM_POWERBROADCAST` and a 30 s comparison of the wall clock with `QueryUnbiasedInterruptTime` (a gap over 60 s is logged as a sleep).
- `winshell-app` is the activation target: a small window and the single-instance pipe `\\.\pipe\lilith-spike-winshell-app`. Every start logs its raw `GetCommandLineW` to `%LOCALAPPDATA%\LILITH-spike\winshell\events.jsonl`. A second launch (B) reads the running instance's (A's) `{"app", "pid"}`, checks with `GetNamedPipeServerProcessId` and `QueryFullProcessImageNameW` that A runs the same exe, calls `AllowSetForegroundWindow(A)`, sends `{"args": [<url>]}`, reads `{"ok": true}` and exits; A calls `SetForegroundWindow` (with `--recipe fallback`: also `AllowSetForegroundWindow` for itself and `SwitchToThisWindow` when that fails). One second after asking for the front, a window logs whether `GetForegroundWindow()` is it and whether `GetGUIThreadInfo` of the foreground thread names it as the focus window. `--blocker` opens another window that takes the front and serves no pipe.
- `winshell-hello` (console) runs S1.8's steps one command at a time: `supported`, `create`, `sign`, `tpm`, `verify`, `delete`, `exists`, `dpapi`. The challenge is one fixed 32-byte value compiled into the crate.
- `winshell-tool` (console) is the scripts' helper: it starts `winshell-core` detached, writes and reads the shortcut through `IShellLinkW` and `IPropertyStore` (`System.AppUserModel.ID` as a `VT_LPWSTR`), reads `ToastNotifier::Setting()` and the notification centre's history for the AUMID, calls `ShellExecuteW`, reports the token's elevation and integrity level and the foreground window, and writes the `.wsb` file. It is a fourth binary beside the three the plan names, so the scripts never need a compiled C# helper.

Pure helpers (the first-argument split of the raw command line, removing one pair of quotes, quoting a command line for `CreateProcessW`, toast and `.wsb` XML with escaping, nearest-rank percentiles, base64url, the argument parser) have unit tests, and two integration tests check that the detached spawn returns at once with its stdout piped and that `inside.ps1` refuses to run outside the Sandbox: `cargo test` in `spikes/winshell`.

**Step 2, on the host** (`pwsh -NoProfile -File spikes/winshell/run-spike.ps1`, from a non-elevated terminal; it refuses to run elevated). The script registers the shortcut `<Programs>\LILITH Spike.lnk` and `HKCU\Software\Classes\lilspike` in Appendix G's shape (`(Default) = "URL:LILITH (Spike)"`, an empty `URL Protocol`, `DefaultIcon = "<exe>",0`, `shell\open\command = "<exe>" "%1"`, where `<exe>` is `winshell-app.exe`), runs each check, asks the owner a yes-or-no question wherever a bar needs eyes, and writes `spikes/winshell/results/checks.json`. Its `finally` block removes everything it wrote, each step even when an earlier one fails, and checks that it is gone: the credential counts as gone only when `OpenAsync` answers `NotFound` (or Hello isn't supported), and no `winshell-core` may still be running. How each bar is read:

- S1.1: `cargo clean -p winshell --release`, then `cargo build --release --locked`; the `warning` lines are counted. The feature list is the one in `spikes/winshell/Cargo.toml`.
- S1.2: three toasts with no launch URL; the owner answers whether each popped; `Setting()` comes from the sender. The recorded check then removes the shortcut, writes `HKCU\Software\Classes\AppUserModelId\LILITH.Spike.Notify` with a `DisplayName`, posts one toast, removes that key and writes the shortcut again.
- S1.2p (recorded; added after run 1, see section 5): does a toast nobody clicks stay in the notification centre after its banner times out? One toast with the plain shortcut (the AUMID only) and one with the shortcut also carrying `System.AppUserModel.ToastActivatorCLSID`, whose CLSID is registered per user with a `LocalServer32` of `winshell-app.exe`. Each is read from `ToastNotificationManager::History` at once and again 15 s after the banner's time (the user's "dismiss notifications after" setting, 5 s by default), and the owner says whether Win+N lists it. S1.3 and S1.4 then use the shortcut with the CLSID.
- S1.3: six confirmation toasts (launch and "Open" both `lilspike:confirm/cf_0123456789abcdef`); the owner clicks the body three times, then the button three times; each new `winshell-app` start's command line is compared, case-sensitively, with `"<full path of winshell-app.exe>" "lilspike:confirm/cf_0123456789abcdef"`. Recorded: Edge opening the raw ref from a local HTML file, and the Run dialog with `lilspike:open/<base64url>` with and without a trailing `/`. The base64url target holds `?`, `~` and a non-ASCII letter so that the encoding contains `_`.
- S1.3 and S1.4, after run 1: when no click arrives within 60 s, the owner is asked whether the toast was missed; a missed toast is posted again (up to 3 posts), and every missed post is recorded with the trial. A trial whose click never happens can't change a decided result. S1.3 is FAIL when a click that arrived wasn't exact, otherwise INCOMPLETE when a trial never got a click. In S1.4 a click counts as soon as the second launch (B) starts, so a hand-off that then fails is a FAIL of that recipe and starts the fallback recipe, not an invalid trial. S1.4 is FAIL on a valid failure (without A, or with A after the fallback recipe also failed), and INCOMPLETE only when invalid trials could still change the verdict.
- S1.4: each trial first checks its precondition, that the blocker window holds the front. After run 1 (section 5), when the blocker's own `SetForegroundWindow` doesn't get it there, the owner clicks the blocker's title bar once and the script checks `GetForegroundWindow` itself; a trial whose precondition can't be met is invalid, and invalid trials make the verdict INCOMPLETE rather than FAIL. The fallback recipe runs only when a valid with-A trial failed. With A: A starts, then the blocker window takes the front, then a toast; after the owner's click, A's own check must show it in front with focus. Without A: only the blocker, then a toast; the window of the launch the click starts must show itself in front with focus. When a with-A trial fails, the five with-A trials run again with `--recipe fallback`.
- S1.5: the progress toast for 20 s (all 20 updates must return `Succeeded`; the owner answers whether it popped again); the owner dismisses it in the notification centre; one more update must return `NotificationNotFound`; `RemoveGroupedTagWithId` then a new toast with the same Tag (the owner answers whether it popped); a `SuppressPopup` toast (the owner answers whether it stayed hidden and whether it is in the notification centre).
- S1.6: (a) 30 s at the desktop, every poll `QUNS_ACCEPTS_NOTIFICATIONS`, and 100 back-to-back calls timed at the start; (b) 60 s with the owner's fullscreen Direct3D program, PASS when at least 5 polls in a row (10 s) read `QUNS_RUNNING_D3D_FULL_SCREEN` or `QUNS_BUSY` (the first 20 s are the owner's set-up time; the time to the first such reading is recorded); (c) and (d) the same timing, values recorded.
- S1.7: `powercfg /a` and the sleep timeout (`powercfg /query SCHEME_CURRENT SUB_SLEEP STANDBYIDLE`, AC or DC by the battery's state) are read by the script. The owner runs `powercfg /requests` in an elevated terminal while the request is held and after it is cleared, and notes any other requester listed under SYSTEM. When the timeout is finite, the request is held for the timeout plus 5 minutes plus 30 s with no input; PASS when the core logged no `PBT_APMSUSPEND` and no clock gap over 60 s, and the System log holds no Kernel-Power sleep or Modern Standby entry (ids 42 and 506) since the request was set. An unparsed timeout is recorded as unknown, not as "never". Then, with no request held, the owner puts the PC to sleep and wakes it; PASS when the hidden window logged `PBT_APMSUSPEND` and `PBT_APMRESUMEAUTOMATIC`.
- S1.8: the steps (a)–(f) in order from the owner's Windows Terminal, the owner answering whether each prompt was in front; (c) compares the hex of 10 signatures from two processes. The route follows the bar's rule.

**Step 2b, in Windows Sandbox**, as first planned. *Superseded by the scope cut at the end of this section: the `-Observe` run, `-QtGrabArgs` and the offscreen launch are gone, and the Qt item grabs the on-screen window only.* It refuses to start while any Sandbox is running. For each run the script builds a bundle (`inside.ps1`, `config.json`, a marker file, the four exes with the three VC++ runtime DLLs beside them, the three DLLs again alone in `vcrt\`, and the crate's unit-test exe in `rusttest\`), copies Task 0's deploy folder once, makes an empty results folder (granting SYSTEM modify when it isn't inherited), and writes a `.wsb` with networking, clipboard redirection, audio and video input and printer redirection off that maps the bundle read-only at `C:\lil\in`, the deploy copy read-only at its own host path and the results folder writable at `C:\lil\out`, with the logon command `powershell.exe -ExecutionPolicy Bypass -File C:\lil\in\inside.ps1`. The Qt item runs the deploy folder's exe with `QSG_INFO=1` and `QT_FORCE_STDERR_LOGGING=1` (the RHI backend is read from its log): offscreen with `QT_QPA_PLATFORM=offscreen` and the app's own grab to a PNG (the arguments are `run-sandbox.ps1 -QtGrabArgs`, default `--grab {png}`), and on screen as a visible window captured with `CopyFromScreen`; a grab is non-flat when a 64 × 64 sample grid holds more than one colour. A missing VC++ DLL can't stop the run with a dialog: `inside.ps1` sets `SEM_FAILCRITICALERRORS`.

Since run 1, an error inside one check is recorded as that check's `ERROR` verdict (with the message and line) and the run goes on to the next check; only the S1.1 and S1.2 stop rule ends a run. The console, with every question and answer, is kept as `results/raw/console.log`, and a rerun moves the earlier `checks.json` and `raw/` into `results/run-<UTC time>/`.

**Automation round: the method of run 3** (owner direction 2026-10-23; fix rounds 1–4 after its reviews). Run 3 ran this code's attended stage on `093e918`; the stage commands and the watched Sandbox run it used are gone since the scope cut (below). The scripts detected instead of asking (`spikes/winshell/uia.ps1`), and every item recorded the method that decided it:

- **A toast's popup:** UI Automation. Microsoft doesn't document which process or window hosts toasts, so nothing names one. Each toast's text carries a random nonce (the progress and repost toasts too), and the search covers only top-level windows that appeared after the post, plus the hosts learned that way earlier in the run; their process name and window class are recorded. A calibration toast at setup proves that UIA can see this PC's toasts.
  - Popups are counted as appearances. An appearance ends only after at least 2 consecutive clean absent readings spanning more than 1 s, and a poll whose search threw counts as unknown, not as absent. Each reading records the element's rectangle and `IsOffscreen`.
  - "Not seen" decides only after a toast has been found in the run and with at least 4 clean readings; otherwise the owner is asked. The quiet toast's "no pop" also needs a normal control toast, posted just before it, to have been seen.
- **S1.5's "doesn't pop again":**
  - two or more popups is FAIL;
  - one popup is the owner's decision (run 2's owner saw a second pop, and a banner that re-animates in place stays one element, which UIA counts once);
  - zero popups never decides: the owner is asked, and that is recorded.
- **The notification centre:** `ToastNotificationManager::History` decides what is in it, and UIA records the same after the script opens it (Win+N). The script closes it with Esc only while it is the foreground window, else with Win+N, and sends nothing to a centre it didn't identify. `UserNotificationListener` isn't used: it needs the `userNotificationListener` capability in a package manifest, which an unpackaged program can't declare.
- **Every UIA action on a toast is scoped to that toast:** the nearest ancestor of its nonce text whose subtree holds no other spike nonce and at most one "Open" button. S1.3's button is that toast's own "Open". S1.5's dismissal is that toast's own dismiss or close button, found after hovering over the entry, and the owner closes it when there is none. Nothing whose Name or AutomationId says "clear" or "all" is ever pressed.
- **Synthesized clicks** (S1.3, the S1.4 blocker, S1.4's recorded set, the Sandbox cover) are one `SendInput` call that carries the position (`MOUSEEVENTF_MOVE | ABSOLUTE | VIRTUALDESK` on the button down and up). Right before it, `WindowFromPhysicalPoint` must find the expected process and class at the point. The `SendInput` return value is checked, and the cursor is put back.
  - Every synthesized click, key or hover holds back while the owner has given input in the last 2 s (`GetLastInputInfo`, told apart from the script's own injections). It retries 5 times, 2 s apart, then hands the step to the owner.
  - A yellow HANDS OFF line, naming Ctrl+C, comes before each stretch.
- **S1.4's bar keeps the owner's own click.** Its question is the foreground right a real click gives. An `InvokePattern` call gives no input at all, and Microsoft's foreground rules (`SetForegroundWindow`'s "received the last input event") don't say that injected input counts the same as a person's, so a synthetic click can't answer the question honestly. Five synthetic-click trials are recorded beside it (not the bar), which shows whether a test runner could stand in for the click.
- **S1.8 "in front":** `GetForegroundWindow` and `GetLastInputInfo`, sampled every 150 ms while each Hello call runs.
  - Readings with no foreground window are skipped.
  - The prompt is the first window of another process than the terminal, explorer excluded.
  - If the owner gave input since the call started, before that window came forward, the result is "owner-assisted", not "in front".
- **S1.7:**
  - The owner's elevated `powercfg /requests` listing is not repeated: the listing of 2026-10-23 stands for the bar.
  - The stay-awake wait doesn't start while a Windows Sandbox runs, or while `ES_SYSTEM_REQUIRED` is already in force (another requester; it rechecks for 10 minutes first). Either is recorded as "not decisive", which makes the verdict INCOMPLETE.
  - The execution state and the idle timer (`CallNtPowerInformation`, read only) are recorded before and every 60 s during the hold.
  - Input during the wait restarts it from that input, up to 3 times.
  - The core holding the request watches the script's process and releases the request if it goes.
  - The sleep timeout is only ever read, and the wait follows whatever value it finds.

**Fix round 4, the method of run 3.**
- **A strict-mode simulation** (`spikes/winshell/tests/simulate.ps1`, run by `cargo test`). **For Task 28 (Windows Hello).** **This changes Task 28's "Consumes: Task 1's route. Only that route is built"** (plan line 1529). The spike hands Task 28 no route. The KEK route's crypto works on this PC: create, 10 identical signatures across two processes, delete, TPM 2.0 (S1.8). - The KEK route needs the window-owned calls: `KeyCredentialManager.RequestCreateForWindowAsync(WindowId, name, option)` and `KeyCredential.RequestSignForWindowAsync(WindowId, data)` (learn.microsoft.com/uwp/api/windows.security.credentials.keycredentialmanager.requestcreateforwindowasync and …keycredential.requestsignforwindowasync, winrt-28000). They are not in `windows 0.62.2`, so they need bindings generated from newer metadata (`windows-bindgen`) or a raw COM binding.
- The DPAPI-with-gate route's prompt is owned through `IUserConsentVerifierInterop::RequestVerificationForWindowAsync(HWND, …)` (learn.microsoft.com/windows/win32/api/userconsentverifierinterop/nf-userconsentverifierinterop-iuserconsentverifierinterop-requestverificationforwindowasync), which is in the crate; run 3 passed it `GetConsoleWindow()`. Under Windows Terminal that is the ConPTY pseudo-console window, which is never in front; owning the prompt by a real window that is in front is the first thing to try.
- Proving that the prompt comes to the front of every application, a fullscreen one included, is Task 28's. This spike shows only what is above. The consent prompt, owned by a window that was not in front, was in front after owner input. The create prompt has no owner window (`RequestCreateAsync` takes none) and was not seen in front before owner input.
