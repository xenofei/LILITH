# 11 Windows integration: toasts, activation, foreground, fullscreen, keep-awake and Windows Hello

Date: 2026-10-21

Status: sections 1–4 are written and committed before anything runs (plan 4a, Task 1, Step 1). The owner-present runs (Step 2 on the host, Step 2b in Windows Sandbox) fill sections 5–8.

## 1. Question

The rules this spike settles: APP-014, APP-020, APP-022, APP-146, ARCH-127, CORE-160 and QA-088, and, for the desktop test group, QA-042 (P4a-R31). ARCH-127 is the keep-awake rule plan 4a's Task 2 adds; Appendix G is the spec appendix the same task writes.

The questions, one per check:

- Which `windows` 0.62 features does the suite need for toasts, the shortcut, Windows Hello, the fullscreen state and the power request? (S1.1)
- Can a windowless, detached process post toasts under the AUMID of a per-user Start-menu shortcut? (S1.2)
- What exactly does a protocol activation's raw command line hold: from a toast's body, from its button, from a browser and from the Run dialog? (S1.3)
- Which foreground recipe brings the running instance to the front when a toast click starts a second launch? (S1.4)
- Do progress toasts update in place, without popping again, and behave as documented once dismissed or removed? (S1.5)
- What does `SHQueryUserNotificationState` report at the desktop, in a fullscreen Direct3D program, in fullscreen video and in a slide show, and how fast is it? (S1.6)
- Which power-request API keeps the PC awake while a GPU job runs, and does the core see a sleep and a wake? (S1.7)
- Which Windows Hello route can `lil dev approve` use: a key-encryption key from a Hello signature, DPAPI behind a Hello check, or a passphrase only? (S1.8)
- Which of these desktop checks work inside Windows Sandbox, unattended, and how long does a run take? (S1.9)

## 3. Method

`spikes/winshell/` is a standalone crate (not a workspace member) with four binaries:

- `winshell-core` (`windows_subsystem = "windows"`) is the windowless sender. It is always started with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` and no inherited handles, as `lil-client` starts the core, and writes its result as JSON to the file `--out` names. It posts toasts (Appendix G's XML: `launch` with `activationType="protocol"`, an "Open" action for the confirmation form, Tag and Group, `SuppressPopup`), runs the progress toast (data binding, `NotificationData` with `SequenceNumber` 1 and one update a second by Tag and Group), `Remove(tag, group)`, the 2 s `SHQueryUserNotificationState` poll with 100 timed calls, and the power request: `PowerCreateRequest` with a simple reason string and `PowerSetRequest(PowerRequestSystemRequired)` (or, on the FAIL path, `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` from a dedicated thread), held until a flag file appears, with a hidden top-level window that logs every `WM_POWERBROADCAST` and a 30 s comparison of the wall clock with `QueryUnbiasedInterruptTime` (a gap over 60 s is logged as a sleep).
- `winshell-app` is the activation target: a small window and the single-instance pipe `\\.\pipe\lilith-spike-winshell-app`. Every start logs its raw `GetCommandLineW` to `%LOCALAPPDATA%\LILITH-spike\winshell\events.jsonl`. A second launch (B) reads the running instance's (A's) `{"app", "pid"}`, checks with `GetNamedPipeServerProcessId` and `QueryFullProcessImageNameW` that A runs the same exe, calls `AllowSetForegroundWindow(A)`, sends `{"args": [<url>]}`, reads `{"ok": true}` and exits; A calls `SetForegroundWindow` (with `--recipe fallback`: also `AllowSetForegroundWindow` for itself and `SwitchToThisWindow` when that fails). One second after asking for the front, a window logs whether `GetForegroundWindow()` is it and whether `GetGUIThreadInfo` of the foreground thread names it as the focus window. `--blocker` opens another window that takes the front and serves no pipe.
- `winshell-hello` (console) runs S1.8's steps one command at a time: `supported`, `create`, `sign`, `tpm`, `verify`, `delete`, `exists`, `dpapi`. The challenge is one fixed 32-byte value compiled into the crate.
- `winshell-tool` (console) is the scripts' helper: it starts `winshell-core` detached, writes and reads the shortcut through `IShellLinkW` and `IPropertyStore` (`System.AppUserModel.ID` as a `VT_LPWSTR`), reads `ToastNotifier::Setting()` and the notification centre's history for the AUMID, calls `ShellExecuteW`, reports the token's elevation and integrity level and the foreground window, and writes the `.wsb` file. It is a fourth binary beside the three the plan names, so the scripts never need a compiled C# helper.

Pure helpers (the first-argument split of the raw command line, removing one pair of quotes, toast and `.wsb` XML with escaping, nearest-rank percentiles, base64url, the argument parser) have unit tests: `cargo test --lib` in `spikes/winshell`.

**Step 2, on the host** (`pwsh -NoProfile -File spikes/winshell/run-spike.ps1`, from a non-elevated terminal; it refuses to run elevated). The script registers the shortcut `<Programs>\LILITH Spike.lnk` and `HKCU\Software\Classes\lilspike` in Appendix G's shape (`(Default) = "URL:LILITH (Spike)"`, an empty `URL Protocol`, `DefaultIcon = "<exe>",0`, `shell\open\command = "<exe>" "%1"`, where `<exe>` is `winshell-app.exe`), runs each check, asks the owner a yes-or-no question wherever a bar needs eyes, and writes `spikes/winshell/results/checks.json`. Its `finally` block removes everything it wrote and checks that it is gone. How each bar is read:

- S1.1: `cargo clean -p winshell --release`, then `cargo build --release --locked`; the `warning` lines are counted. The feature list is the one in `spikes/winshell/Cargo.toml`.
- S1.2: three toasts with no launch URL; the owner answers whether each popped; `Setting()` comes from the sender. The recorded check then removes the shortcut, writes `HKCU\Software\Classes\AppUserModelId\LILITH.Spike.Notify` with a `DisplayName`, posts one toast, removes that key and writes the shortcut again.
- S1.3: six confirmation toasts (launch and "Open" both `lilspike:confirm/cf_0123456789abcdef`); the owner clicks the body three times, then the button three times; each new `winshell-app` start's command line is compared, case-sensitively, with `"<full path of winshell-app.exe>" "lilspike:confirm/cf_0123456789abcdef"`. Recorded: Edge opening the raw ref from a local HTML file, and the Run dialog with `lilspike:open/<base64url>` with and without a trailing `/`. The base64url target holds `?`, `~` and a non-ASCII letter so that the encoding contains `_`.
- S1.4: with A: A starts, then the blocker window takes the front, then a toast; after the owner's click, A's own check must show it in front with focus. Without A: only the blocker, then a toast; the window of the launch the click starts must show itself in front with focus. When a with-A trial fails, the five with-A trials run again with `--recipe fallback`.
- S1.5: the progress toast for 20 s (all 20 updates must return `Succeeded`; the owner answers whether it popped again); the owner dismisses it in the notification centre; one more update must return `NotificationNotFound`; `RemoveGroupedTagWithId` then a new toast with the same Tag (the owner answers whether it popped); a `SuppressPopup` toast (the owner answers whether it stayed hidden and whether it is in the notification centre).
- S1.6: (a) 30 s at the desktop, every poll `QUNS_ACCEPTS_NOTIFICATIONS`, and 100 back-to-back calls timed at the start; (b) 60 s with the owner's fullscreen Direct3D program, PASS when at least 5 polls in a row (10 s) read `QUNS_RUNNING_D3D_FULL_SCREEN` or `QUNS_BUSY` (the first 20 s are the owner's set-up time); (c) and (d) the same timing, values recorded.
- S1.7: `powercfg /a` and the sleep timeout (`powercfg /query SCHEME_CURRENT SUB_SLEEP STANDBYIDLE`, AC or DC by the battery's state) are read by the script. The owner runs `powercfg /requests` in an elevated terminal while the request is held and after it is cleared. When the timeout is finite, the request is held for the timeout plus 5 minutes plus 30 s with no input; PASS when the core logged no `PBT_APMSUSPEND` and no clock gap. Then, with no request held, the owner puts the PC to sleep and wakes it; PASS when the hidden window logged `PBT_APMSUSPEND` and `PBT_APMRESUMEAUTOMATIC`.
- S1.8: the steps (a)–(f) in order from the owner's Windows Terminal, the owner answering whether each prompt was in front; (c) compares the hex of 10 signatures from two processes. The route follows the bar's rule.

**Step 2b, in Windows Sandbox** (`pwsh -NoProfile -File spikes/winshell/run-sandbox.ps1 -Runs 3`, then `-Observe` for the host-state observation). For each run the script builds a bundle (`inside.ps1`, `config.json`, the four exes with the three VC++ runtime DLLs beside them, the three DLLs again alone in `vcrt\`, and the crate's unit-test exe in `rusttest\`), copies Task 0's deploy folder once, makes an empty results folder (granting SYSTEM modify when it isn't inherited), and writes a `.wsb` with networking off that maps the bundle read-only at `C:\lil\in`, the deploy copy read-only at its own host path and the results folder writable at `C:\lil\out`, with the logon command `powershell.exe -ExecutionPolicy Bypass -File C:\lil\in\inside.ps1`. With the `wsb` CLI it runs `wsb start --config <xml>` and then `wsb connect --id <id>` (the logon command needs a user session); otherwise `WindowsSandbox.exe <file.wsb>`. It waits 120 s for `started.json`, then for `done.json`, then for the Sandbox to close (by `shutdown /s /t 0` inside, else `wsb stop --id`, else by ending the `WindowsSandbox*` processes), samples the process names while it runs, and judges each item from the files. `inside.ps1` runs the items of the bar; the foreground item's second window is the blocker, which, once in front, starts B itself with `ShellExecuteW`, standing in for the toast host. The Qt item runs the deploy folder's exe with `QSG_INFO=1` and `QT_FORCE_STDERR_LOGGING=1` (the RHI backend is read from its log): offscreen with `QT_QPA_PLATFORM=offscreen` and the app's own grab to a PNG (the arguments are `run-sandbox.ps1 -QtGrabArgs`, default `--grab {png}`), and on screen as a visible window captured with `CopyFromScreen`; a grab is non-flat when a 64 × 64 sample grid holds more than one colour. A missing VC++ DLL can't stop the run with a dialog: `inside.ps1` sets `SEM_FAILCRITICALERRORS`.

Re-run: the two commands above. `spikes/winshell/OWNER-STEPS.md` lists what each step shows, what the owner does, how long it takes, and what it writes and removes.

## 4. Pass criteria

Copied verbatim from plan 4a, Task 1, before the run. Not edited after it.

- **S1.1 Crate surface:** the spike builds with 0 warnings using `UI::Notifications::{ToastNotificationManager, ToastNotification, NotificationData}`, `Data::Xml::Dom::XmlDocument`, `Security::Credentials::KeyCredentialManager`, `Win32::System::WinRT::IUserConsentVerifierInterop`, `Win32::UI::Shell::SHQueryUserNotificationState`, `Win32::System::Power::{PowerCreateRequest, PowerSetRequest, PowerClearRequest}`, `Win32::UI::Shell::PropertiesSystem::IPropertyStore` and `Win32::Security::Cryptography::{CryptProtectData, CryptUnprotectData}`. The feature list is recorded for Task 5.
- **S1.2 Windowless sender** (APP-022): `winshell-core.exe`, started with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`, posts a toast under AUMID `LILITH.Spike.Notify`, with a per-user shortcut `<Programs>\LILITH Spike.lnk` carrying that AUMID. PASS = the owner sees it pop, 3 times of 3, and `ToastNotifier::Setting()` is `Enabled`. Recorded, not a bar: whether a toast shows with the shortcut removed and only `HKCU\Software\Classes\AppUserModelId\LILITH.Spike.Notify` present.
- **S1.3 Protocol activation** (APP-020): `HKCU\Software\Classes\lilspike` registered as Appendix G's registration says, with scheme `lilspike`. PASS = a click on the toast's body and one on its button each start `winshell-app.exe` with `GetCommandLineW` exactly `"<exe>" "lilspike:confirm/cf_0123456789abcdef"`, 3 times of 3 each. Recorded: the raw command line when Edge opens `lilspike://0123456789abcdef/sketchbook/lantern@1.0.0#sha256=<64 hex>` from a local HTML file, and when the Run dialog opens `lilspike:open/<base64url>` (encoding, a trailing `/`, quotes). FAIL (the argument arrives split, re-quoted or percent-encoded) → P4a-R3's grammar is changed to match what arrives before Task 2 writes Appendix G, and the change is reported.
- **S1.4 Foreground** (APP-014): with `winshell-app.exe` A running behind another focused window, a toast click starts B, which reads A's pid over the spike's single-instance pipe, calls `AllowSetForegroundWindow(A)`, passes the argument and exits; A calls `SetForegroundWindow`. PASS = `GetForegroundWindow()` is A's window and A has keyboard focus, 5 times of 5; with no A running, B's own window comes to the front, 5 times of 5. FAIL → the foreground recipe changes (the running instance also calls `AllowSetForegroundWindow` for its own windows and uses `SwitchToThisWindow` as a fallback) and the check runs again; still failing → the owner hears before Task 2, and the confirm window falls back to a flashing taskbar button.
- **S1.5 Progress toasts** (APP-146): a toast with Tag `j_spike`, Group `job_progress` and data binding, updated once a second for 20 s. PASS = every `Update` returns `Succeeded` and the toast doesn't pop again; after the owner dismisses it, `Update` returns `NotificationNotFound`; at the end `Remove(tag, group)` then a new toast pops; a toast with `SuppressPopup = true` lands in the notification centre without popping (owner confirms). FAIL → progress toasts are left out of plan 4a (the `job_progress` category stays, off, with no toasts) and the owner hears before Task 2.
- **S1.6 Fullscreen poll** (CORE-160, APP-146): `SHQueryUserNotificationState` every 2 s while the owner (a) works at the desktop, (b) runs a fullscreen Direct3D game or program, (c) plays a fullscreen video in a browser, (d) runs a presentation if one is at hand. PASS = (a) gives `QUNS_ACCEPTS_NOTIFICATIONS`; (b) gives `QUNS_RUNNING_D3D_FULL_SCREEN` or `QUNS_BUSY`; the call's p99 < 1 ms over 100 calls. (c) and (d) are recorded. The poll runs from `winshell-core.exe`, the detached windowless process, as the core will. FAIL → fullscreen auto-pause and the quiet mode use only the values that did work, and the owner hears before Task 2.
- **S1.7 Keep-awake** (ARCH-127): the detached `winshell-core.exe` holds `PowerSetRequest(PowerRequestSystemRequired)` on a `PowerCreateRequest` object with a reason string. PASS = `powercfg /requests`, which the owner runs in an elevated terminal, lists it under SYSTEM while held and not after `PowerClearRequest`; and, when this PC's sleep timeout is finite, the PC stays awake 5 minutes past it with no input while the request is held (owner present; recorded as skipped when the timeout is "never"); `powercfg /a` (owner) records whether Modern Standby is present; and the spike's hidden window receives `PBT_APMSUSPEND` and `PBT_APMRESUMEAUTOMATIC` across one sleep (owner present). If those messages don't arrive, ARCH-127's sleep-gap record falls back to comparing the wall clock with the monotonic clock every 30 s, a jump of more than 60 s counting as a sleep. FAIL → the same checks with `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` from a dedicated thread; if both fail, ARCH-127's "can't be held" path.
- **S1.8 Windows Hello** (QA-088): from `winshell-hello.exe` in Windows Terminal: (a) `KeyCredentialManager::IsSupportedAsync()` is true; (b) `RequestCreateAsync("LILITH-spike-kek", ReplaceExisting)` shows the Hello prompt in front of the terminal; (c) `OpenAsync`, then `RequestSignAsync` over one fixed 32-byte challenge 5 times in one process and 5 times in a second process, gives 10 byte-identical signatures; (d) a TPM 2.0 is present (`Tbsi_GetDeviceInfo`); (e) `IUserConsentVerifierInterop::RequestVerificationForWindowAsync(GetConsoleWindow(), …)` shows the prompt in front and returns `Verified`; (f) `DeleteAsync` removes the credential. The route: **KEK** when (a), (b), (c), (d) and (f) pass; else **DPAPI with the Hello gate** when (e) passes and `CryptProtectData`/`CryptUnprotectData` round-trip; else **passphrase only**, reported to the owner.
- **S1.9 Inside Windows Sandbox** (QA-042, P4a-R31; owner decision 2026-10-22). It runs after Task 0's Step 2, because its Qt item and its deploy mapping use Task 0's deploy folder, `spikes/app-shell/build/deploy`. **Owner step first** (about 10 minutes with the restart): turn on the Windows Sandbox feature once (Settings → Optional features → "More Windows features" → Windows Sandbox), which needs virtualization on in the firmware; agents change no system setting. The scripts inside are written for Windows PowerShell 5.1 (`pwsh` isn't in the Sandbox image), and the `LogonCommand` is `powershell.exe -ExecutionPolicy Bypass -File C:\lil\in\inside.ps1`. The spike's `run-sandbox.ps1` then writes a `.wsb` that maps the spike's bundle read-only, a copy of the spike's deploy folder read-only at the same absolute path as on the host (to check that a `SandboxFolder` outside the default places works), and an empty results folder writable (made before the start, readable by SYSTEM, as Sandbox shares run as SYSTEM). Its logon command runs `inside.ps1`, which writes `started.json` at once, runs every item below, writes one JSON file per item and `done.json` to the results folder, then shuts the Sandbox down. Every bar is read from those files by `run-sandbox.ps1`, unattended:
  - **elevation:** `elevation.json` records the logon process's `TokenElevation` and integrity level. If it is elevated, `inside.ps1` repeats the toast and foreground items under a de-elevated launch (a scheduled task with `/RL LIMITED`, then `runas /trustlevel:0x20000` if that fails), records which launch worked, and the items below are judged on that run. If neither gives a non-elevated token, the toast and foreground items FAIL and go to the owner.
  - **toast:** `toast.json` holds `ToastNotifier::Setting()` and whether `ToastNotificationManager::History().GetHistory("LILITH.Spike.Notify")` holds the posted Tag. PASS = `Enabled` and the Tag is there.
  - **protocol:** `protocol.json` holds whether `HKCU\Software\Classes\lilspike\shell\open\command` exists after registration, and the raw `GetCommandLineW` that `ShellExecuteW("lilspike:confirm/cf_0123456789abcdef")` delivered. PASS = present, and the argument exactly `"lilspike:confirm/cf_0123456789abcdef"`.
  - **foreground:** `foreground.json` holds A's pid and window, the pid of a second window the script itself brought to the front first, and `GetForegroundWindow()`'s owner pid after B's hand-off. PASS = A's pid.
  - **power:** `power.json` holds `PowerSetRequest`'s result and whether `powercfg /requests`, run from the elevated logon context, lists it. PASS = listed. This proves only the API inside a VM; S1.7 on the host stays the real check that the PC stays awake.
  - **Rust exe:** `rust.json` holds the exit code of one dynamically linked Rust test exe run once with the three VC++ DLLs on `PATH` and once without them. PASS = it runs with them (the runner bundles them either way); the run without them is recorded.
  - **Qt windows:** `qt.json` holds the spike app's grab statistics offscreen (`QT_QPA_PLATFORM=offscreen`) and on the Sandbox's own screen (visible window, non-flat grab), and the RHI backend Qt chose. PASS = both grabs are non-flat.
  - **lifecycle:** `lifecycle.json` and the host log record the Sandbox's version and kind (inbox, or the Store version with the `wsb` CLI), which availability check worked (`wsb list` exiting 0 where the CLI exists; else `WindowsSandbox.exe` present and a run reaching `started.json` within 120 s), which stop worked (`shutdown /s /t 0` inside; `wsb stop --id`; ending the `WindowsSandbox.exe` process the script started and its client), the Sandbox's process names while it runs (for `running()`), and the time from start to closed. PASS = a detection and a stop that both work, and a whole run under 10 minutes (part of PASS).
  - **host state** (one owner-present observation, about 15 minutes): the owner watches one run's toast pop in the Sandbox window (the only on-screen item), then the toast, foreground and Qt items run again with the Sandbox window behind other windows, and once more with the host locked. Recorded, not a bar; Task 30 tells the owner what not to do during a run from these results.
  - PASS = every bar above, 3 runs of 3. FAIL on any item → that item's tests can't use the runner: stop and ask the owner before Task 2 (running them in the owner's own session would need a QA-042 amendment, which is the owner's call); the other items still use the runner.
- **Cleanup:** PASS = afterwards the spike's shortcut, `HKCU\Software\Classes\lilspike`, `HKCU\Software\Classes\AppUserModelId\LILITH.Spike.Notify` and the credential are gone, checked by the script.

If S1.1 or S1.2 fails, stop: the result goes to the owner before Task 2 (APP-022).
