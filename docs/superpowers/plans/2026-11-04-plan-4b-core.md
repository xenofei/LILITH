# Plan 4b — Browse and Review Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the core everything the browse-and-review panels (plan 4c) will call, with no Qt: organising marks with `assets.query` filters and facets, saved searches and collections, the status log and deprecation, redirects with moved and copied folder repair, the duplicate finder, whole-asset trash and `trash.restore {to?}`, the thumbnail service, the pick log, version detail and restore as new version, attribution end to end, the round-13 reservations, the ComfyUI inbox, the telemetry and jobs carries, and the store carries; all testable through `lil call`, MCP and Rust tests.

**Architecture:**
- **Spec first** (QA-029): Task 1 writes spec **Appendix H, "Browse and review core (plan 4b clarification)"**, from Global Constraints' "Names that are contracts". No new rule ids (P4b-R1).
- **Manifests stay the source of truth** (Appendix E's decision): marks, takes, the status log, actors and trust records are manifest fields read through `lil-schema` views; collections and redirects are tracked YAML in `registry/`; `index.db` (disposable, schema 2) mirrors them for filters, facets, duplicates and tile fields.
- **One resolver, one status path, one display function:** every ref-to-folder mapping goes through `pipeline::resolve::Resolver` (redirects, trash, live folder wins); every status change goes through `pipeline::status::change_status`, which writes the status log in the same manifest edit; every "which image shows this asset" answer comes from `pipeline::display::display_file`.
- **The thumbnail service** lives in the core's `interchange` module: a renderer registry (`image@1`, `icon@1`), fixed tiers, a cache keyed by content hash in the per-workspace local folder, and `app/thumbs.request`. Untrusted decoding runs bounded, off the async threads, with a panic guard.
- **One protocol bump, 1.3 → 1.4** (Task 10), for every new wire type: `app/thumbs.request`, the two owner-only `app/asset.*` methods, and the confirmation's `files` and `facts`.

**Tech Stack:** Rust 1.99.0 (MSVC), edition 2024, `cargo-nextest`, `cargo-deny`, as in plan 4a. New crate: `image` (decode and encode only, pure Rust). No Qt anywhere in this plan.

**Spec:** `docs/superpowers/specs/2026-10-12-lilith-design.md` (1080 rules; this plan adds none, so `EXPECTED_RULE_COUNT` in `crates/lil-cli/src/dev/spec_report.rs` stays 1080 and that file isn't touched). Terms are those of `docs/GLOSSARY.md`. The plan follows roadmap row 4b (`docs/superpowers/plans/2026-10-12-roadmap.md`) as split by the owner on 2026-11-04 (OD-9 below).

**Execution method:** subagent-driven: a fresh implementer per task, a fresh reviewer per task (adversarial where marked), then a whole-branch review at the end. Every task is Qt-free and testable without a GUI.

**Starts after:** plan 4a is closed (it is, 2026-11-04). Every task branches from `main`.

- **P4b-R1** No new rule ids. Everything is a plan-4b clarification in Appendix H, as plan 4a did with Appendix G. Why: the reservations and rules already exist; `spec_report.rs` (protected) needn't change. Cost if wrong: one id later.

- **P4b-R3 (mismatch 3: what a take is).** A **take** is one output of a run: its primary file plus optional companions. `candidate_runs[].files[].take` (1-based) groups files and `primary: true` marks one per take. Flags and ratings live on the take's primary file entry; `asset.mark {take}` and `{file}` both address it. A run in which no file has `take` reads as: each `candidate`-role file is its own take, numbered in file order, and a `derived`, `repair` or `preview` file joins the take of its `from` file as a companion. APP-163's copy is unchanged ("each candidate is a take" stays true for one-file takes); the glossary's "Take" row gains the companions sentence. Why: CORE-152 put flags on files and CORE-023's reservation on takes; this reads both. Cost if wrong: a view change in `lil_schema::takes`.
- **P4b-R4 (mismatch 4: un-deprecate with no history).** `asset.deprecate` writes `status_before_deprecated` (beside `status_before_stale`/`blocked`) as well as the status-log entry. `deprecated: false` returns to, in order: `status_before_deprecated`; else the `from` of the newest status-log entry whose `to` is `deprecated`; else `approved` when `approved_version` is set; else `in_progress`. `lil_schema::StatusEvent::Undeprecate` is new. Why: older manifests have no log, and a log keeps only 50 entries. Cost if wrong: an older asset returns to `approved` instead of what it was.
- **P4b-R5 (mismatch 1: the shared GPU memory figure).** ARCH-071 says the engine's PDH `Shared Usage` above idle is recorded per job, and the roadmap says plan 3 did it, but the sampler drops `shared_mib` and no table stores it.
